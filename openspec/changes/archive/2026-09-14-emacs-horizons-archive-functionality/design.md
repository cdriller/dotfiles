## Context

`emacs-refactor-horizon-setup` (already applied) introduced `prilepp/define-horizon-type`, a macro that expands to a `*-directory` defvar, `*--list-*`, `*-ensure-file`, and `*-find` for every horizon type, plus (when a link word is given) `org-*-follow`/`org-*-complete` and `*-insert-*-link`. It defines exactly six types today: `proj`, `aor` (link word `area`), `life`, `goals`, `vision` (all in `init-projects.el`), and `actions` (in `init-files.el`, no link word). See proposal.md for why archiving needs to act on all six generically. See specs/emacs-horizon-archive/spec.md and the emacs-keybindings delta for the required behavior.

`prilepp/entity-sources` (`init-find-entity.el`) already has one `consult--multi` source per type (`:items`/`:action`/`:new`/`:link`), keyed by narrow character. `org-refile-targets` is `'((my/org-horizon-files :maxlevel . 3))` where `my/org-horizon-files` recursively lists `.org` files under `~/notes/horizons/` only - archived files living under `~/notes/archive/` are therefore already excluded from refile targets and from the Heading source, with no changes needed there.

## Goals / Non-Goals

**Goals:**
- A registry that the macro populates with each type's identity (slug, directory variable, generated function symbols, link word), so archive logic can iterate over "every horizon type" without hardcoding six cases.
- Generic, idempotent path mirroring between `~/notes/...` and `~/notes/archive/...`.
- Two new interactive commands (archive, restore) that work for any registered type via one implementation.
- A generic fix, applied once via `advice-add` over every registered type's `*-ensure-file`, for the stale-link bug described in the proposal.
- A generic per-buffer `org-archive-location` redirect for every registered type's files.
- Minimal, additive changes to `init-find-entity.el`: extend the six horizon-type sources' `:items`, without touching the five non-horizon sources.

**Non-Goals:**
- No automatic archiving on state change (`DONE`, etc.) for files or headings - both new commands and `org-archive-subtree` are user-invoked only, per explicit decision.
- No UI/command to browse "all archived entries across all types at once" beyond what the extended `C-c n` sources already provide per type.
- No datetree or per-day archive organization; a flat mirrored file/directory structure only, matching the proposal's mirroring model.
- No change to `org-refile-targets`, `my/org-horizon-files`, or agenda file lists - these already exclude `~/notes/archive/` by construction (see Context).

## Decisions

- **Registry shape and population**: `init-horizon-types.el` gains `(defvar prilepp/horizon-types nil "Alist of horizon-type metadata plists, keyed by slug, registered by `prilepp/define-horizon-type'.")` and a helper `(defun prilepp/horizon-type--register (slug plist) (setf (alist-get slug prilepp/horizon-types) plist))`. The macro's expansion gains one more top-level form calling this helper with a plist literal built from its own keyword arguments (`:slug`, `:directory-var`, `:list-fn`, `:ensure-fn`, `:find-fn`, `:link-word`) - all known at macro-expansion time, so this is a plain quoted literal, not a runtime computation. Using `setf`/`alist-get` (upsert, not blind `push`) makes re-evaluating a `prilepp/define-horizon-type` call (e.g. during interactive development with `C-M-x`) idempotent instead of accumulating duplicate registry entries.
- **New file `init-horizon-archive.el`, loaded after both `init-projects` and `init-files`.** The registry must be fully populated (all six `prilepp/define-horizon-type` calls evaluated) before this file's top-level code (the `advice-add` loop, the `org-archive-location` hook setup) runs. `init.el`'s `require` order becomes: `init-org`, `init-horizon-types`, `init-files`, `init-projects`, `init-horizon-archive`, `init-contacts`, `init-calendar`, `init-find-entity`, `init-dashboard` - i.e. one new `require` inserted between `init-projects` and `init-find-entity` (the latter needs the archived-candidate helper functions this file defines).
- **Path mirroring via a single string-prefix substitution, not per-type path arithmetic.** `(defvar prilepp/notes-root (expand-file-name "~/notes/"))` and `(defvar prilepp/archive-root (expand-file-name "~/notes/archive/"))`; `(defun prilepp/archive-path (path) (concat prilepp/archive-root (string-remove-prefix prilepp/notes-root (expand-file-name path))))` and its inverse `prilepp/active-path` (strip `archive-root`, prepend `notes-root`). Every other piece of this design (archive/restore commands, the ensure-fn advice, the `org-archive-location` hook) calls one of these two functions rather than reimplementing the substitution - this is the single place the "mirror `~/notes/X` to `~/notes/archive/X`, keep the `horizons/` segment" rule lives, matching the proposal's requirement.
- **Archive/restore as one generic command each, not six.** `prilepp/archive-entry` prompts `completing-read` over `(mapcar #'car prilepp/horizon-types)` for the type, looks up that type's `:list-fn`/`:directory-var` to prompt for an existing active name, computes the active path, moves the file to `(prilepp/archive-path active-path)` (creating parent directories), and calls `org-id-update-id-locations` with a list containing just that one archived file. `prilepp/restore-entry` is the mirror image: it must list *archived* names for the chosen type - computed by listing `.org` files directly under `(prilepp/archive-path directory-var-value)`, since no generated `list-fn` does this (they only scan the active directory) - then moves the file back via `prilepp/active-path` and refreshes IDs the same way.
- **`org-id-update-id-locations` scope**: pass only the single moved file's new location (as a one-element list), not a full repo/vault rescan. `org-id-update-id-locations` merges the given files' ID locations into the existing `org-id-locations` table rather than replacing it, so this is sufficient to make `id:` links into the moved file resolve again, without the cost of rescanning everything on every archive/restore.
- **Stale-link fix via `advice-add :around` in a `dolist` over the registry, not a change to the macro's generated `*-ensure-file` body.** For each registry entry, wrap its `:ensure-fn` symbol with an `:around` advice closing over that entry's `:directory-var`: compute the would-be active path for the requested name, and if `(file-exists-p (prilepp/archive-path active-path))`, return that archived path directly without calling the original function (which would otherwise create an empty active file); otherwise call the original function unchanged. This keeps `emacs-refactor-horizon-setup`'s macro exactly as it is (no coupling from that already-applied change into this one) and applies uniformly to all six current and any future registered types.
- **`org-archive-location` redirect via a buffer-local hook, not a global default.** A single function added to `find-file-hook` checks whether `buffer-file-name` starts with any registered type's `directory-var` value (iterating the registry); if so, it sets `org-archive-location` buffer-locally to `(concat (prilepp/archive-path buffer-file-name) "::")` (Org's `FILENAME::HEADLINE` format with an empty headline, meaning "append at the end of the target file's top level" - Org's normal behavior for an empty headline part). This only affects buffers visiting horizon-type files; all other Org buffers keep Org's global default. Alternative considered: a single global `org-archive-location` string using Org's own `%s` substitution - rejected because Org's `%s` substitutes only the current file's own name into a *fixed* directory template, which cannot express "same relative path, but under a different root directory" (the actual mirroring rule), so a per-buffer computed value is required.
- **`C-c n` low-priority archived candidates via each horizon-type source's `:items`, not a new source/narrow key.** For each of the six sources in `prilepp/entity-sources`, `:items` becomes `(append (existing-active-list-fn) (prilepp/horizon-archived-names slug))` where `prilepp/horizon-archived-names` lists `.org` files directly under that type's mirrored archive directory (same listing logic as the restore command's name-listing, factored into one shared helper). Appending (not merging/sorting) is what gives archived entries "lowest priority" - `consult--multi` preserves a source's `:items` order in its candidate list, so active entries the source lists first are always shown/selected before archived ones.
- **Archived candidates are visually marked via each source's `:annotate` key, not by altering the candidate string itself.** `consult--multi` supports a per-source `:annotate` function (see its docstring): it is called with the plain candidate string and whatever it returns is displayed as a right-aligned annotation (`consult--annotate-align` handles padding), without changing the string used for lookup, `:action`, `:new`, or `:link`. Each of the six sources computes its `archived` name list once (in the same `let` that already exists for `:items`, to avoid re-listing the archive directory on every keystroke) and adds `:annotate (lambda (n) (when (member n archived) (propertize " (archiviert)" 'face 'completions-annotations)))`. Because `:annotate` receives and returns independently of the candidate string consult passes to `:action`/`:new`/`:link`, the existing closures for those keys need no change - this is the same reasoning that already lets the stale-link-fix advice (see the ensure-fn decision above) work transparently for archived names.
- **Existing `:action`/`:new`/`:link` closures need no change.** Each source's `:action` already calls that type's `*-ensure-file` (e.g. `(prilepp/proj-ensure-file n)`); because the stale-link-fix advice wraps `*-ensure-file` itself, calling it with an archived name now transparently resolves to the archived file instead of creating a new active one. This is the reason the ensure-fn advice is designed as `:around` advice on the existing function rather than a separate lookup path: every existing caller of `*-ensure-file` (link-following, `C-c n`, `prilepp/*-find`) gets the fix for free.
- **Keybindings for the two new commands**: bind under a new `C-c a` prefix (currently unused - verified against every existing `C-c <letter>` binding in the config) as `C-c a a` (`prilepp/archive-entry`) and `C-c a r` (`prilepp/restore-entry`), with a which-key label `"C-c a" "archive"`, following the existing convention of grouping related commands under a mnemonic prefix (e.g. `C-c v` for views).

## Risks / Trade-offs

- [Advice stacking: if this change is ever reloaded/re-evaluated without first removing prior advice (e.g. repeated `M-x eval-buffer` during development), `advice-add` on the same function with an `:around` combinator of the same name is idempotent (Emacs replaces same-named advice), so this is safe as long as the advice function is a named `defun`, not an anonymous `lambda`, in the `dolist`] → Mitigation: define one named `defun prilepp/ensure-file--check-archive (orig-fn directory-var name)` taking `directory-var` via a small named wrapper per registry entry (e.g. `apply-partially`), not an inline anonymous lambda, and confirm via `M-x describe-function` after a reload that only one advice is attached.
- [`prilepp/restore-entry` needs to list archived names, which requires the archive directory to exist - if nothing has been archived yet for a type, the directory may not exist] → Mitigation: `prilepp/horizon-archived-names` (and the restore command's prompt) treats a missing archive directory as "no archived entries" (empty list), matching the existing `*--list-*` functions' `(when (file-directory-p root) ...)` guard pattern.
- [Moving a file with `rename-file`/equivalent while it has unsaved buffer modifications could lose edits, or leave a stale buffer visiting the old (now nonexistent) path] → Mitigation: archive/restore commands operate on the file on disk; if a buffer for that file is open, save it first (or `find-file-noselect` + `save-buffer` before moving) and, after moving, either kill the old buffer or redirect it via `set-visited-file-name` to the new path, so no buffer is left pointing at a deleted file.
- [`org-archive-location`'s buffer-local redirect only takes effect for buffers opened after this change's `find-file-hook` is installed; already-open buffers from before an Emacs restart keep Org's default] → Accepted: consistent with how buffer-local Emacs settings normally take effect; a full restart (already part of every prior change's manual verification) covers this.
- [Six generic commands/hooks operating by iterating a mutable global registry is a new "action at a distance" pattern in this config, compared to the previously fully-static, hand-visible per-type code] → Accepted trade-off, explicitly the point of `emacs-refactor-horizon-setup`: mitigated by keeping the registry population itself simple (one upsert call per macro expansion) and documenting it thoroughly in `init-horizon-types.el`'s Commentary (task-level).

## Migration Plan

Pure Elisp config change; no data migration script needed. The `~/notes/archive/` directory tree does not need to pre-exist - `prilepp/archive-entry` and the `org-archive-location` hook both create missing parent directories on first use (`make-directory ... t`), mirroring the existing `*-ensure-file` pattern. Rollback is `git revert`, since no `~/notes/**` content is touched until a user explicitly archives something; any files already archived by the time of a rollback simply become unreachable via the (now-reverted) commands until this change is reapplied, but remain on disk at their mirrored archive path and can be moved back manually if needed.
