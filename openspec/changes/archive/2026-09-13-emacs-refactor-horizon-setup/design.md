## Context

Six "horizon types" (Project, Area, Life, Goal, Vision in `init-projects.el`; Actions/contexts in `init-files.el`) each implement the same shape by hand: a `*-directory` defvar, a `*--list-*` completion helper, a `*-ensure-file` find-or-create function, and (for five of the six) an `org-*-follow`/`org-*-complete` link-type registration plus an `*-insert-*-link` command. See proposal.md for why this duplication is a problem now (a follow-up archive feature needs the same fix applied to all six).

The six existing implementations are *not* byte-for-byte uniform:
- Directory/function slugs vs. link-type words diverge for Area: the directory variable and list/ensure/find functions use the slug `aor` (`prilepp/aor-directory`, `prilepp/aor--list-aors`, `prilepp/aor-ensure-file`, `prilepp/aor-find`), but the org link type and its follow/complete/insert functions use the word `area` (`"area:"` links, `prilepp/org-area-follow`, `prilepp/org-insert-area-link`). Project/Life/Goal/Vision use the same word for both.
- Default file content on creation differs: Project seeds `"#+TODO: TODO(t) WAITING(w) | DONE(d)\n\n* TODO %s\n"` (with the project name interpolated); Actions seeds `"#+TODO: TODO(t) WAITING(w) | DONE(d)\n\n"` (no interpolation); Area/Life/Goal/Vision seed nothing (empty file).
- Actions has no `org-actions-follow`/`-complete` link type and no `prilepp/actions-insert-*-link` command today - it's structurally the odd one out (list + ensure + find only).

Every generated name is consumed by name elsewhere in the config (`prilepp/entity-sources` in `init-find-entity.el`, `org-refile-targets`/`prilepp/routine--candidates` via `prilepp/aor-directory`, `init-org.el`'s `org-refile-targets`), so whatever mechanism replaces the duplication must keep producing plain, named, interned functions/variables with the exact existing names - not opaque closures stored in a data structure.

## Goals / Non-Goals

**Goals:**
- One shared code-generation mechanism that, given a compact per-type declaration, produces the `*-directory` variable, `*-ensure-file`, `*--list-*`, `*-find` command, and (when a link word is supplied) the `org-*-follow`/`org-*-complete` registration and `*-insert-*-link` command - as real, named, interned `defvar`/`defun` forms (not runtime-dispatched closures), so every existing caller (`init-find-entity.el`, `init-org.el`) keeps working unchanged and `describe-function`/`M-x`/keybindings on any generated function behave exactly as they do today.
- Re-express all six existing types through this mechanism with their current names, directories, default content, and link words preserved exactly, including Area's slug/word split.
- Zero observable behavior change: same keybindings, same which-key labels, same completion candidates, same link types, same file locations and default contents.

**Non-Goals:**
- Adding an `action:` link type or `prilepp/actions-insert-*-link` command for Actions. The proposal left this open ("if added"); this design closes it as **not now** - see Decisions. Actions keeps exactly its current external surface (list/ensure/find only), just re-implemented via the shared mechanism internally. Bringing Actions to full parity (adding the link type) is deferred to the follow-up archive change, since the archive feature is what actually needs every type to support the same "follow a link into it" case Actions currently doesn't expose.
- No changes to archiving behavior, `org-refile-targets`, `org-agenda-files`, or any which-key label text. Those are unaffected by this refactor and are explicitly out of scope (archiving is the next change).
- No introduction of `cl-lib` generics/structs. A plain Emacs Lisp macro is enough for this problem and matches the config's existing plain `defun`/`defvar`/`use-package` style (the config uses no macros or `cl-lib` today).

## Decisions

- **A macro (`prilepp/define-horizon-type`), not a runtime factory/dispatch table.** Alternative considered: a single generic function driven by a per-type alist (directory, link-word, etc.), with commands bound via `apply-partially`/`fset` to anonymous closures. Rejected because: (a) every generated name is referenced *by that exact symbol* elsewhere (`prilepp/aor-directory` in `prilepp/routine--candidates`, `prilepp/proj--list-projects` in `prilepp/entity-sources`) - a table-driven approach would need a second layer of named wrapper `defun`s anyway to expose those symbols, which is more indirection for no benefit; (b) `fset`-bound closures lose docstrings and show as anonymous lambdas in `describe-function`/`C-h f`, which degrades discoverability that the config otherwise leans on heavily (which-key everywhere). A macro expands at load time into ordinary named `defun`/`defvar` forms - identical to what's hand-written today, just generated.
- **Two independent name components per type: a "slug" (directory/list/ensure/find names) and an optional "link word" (link-type string + follow/complete/insert names).** This directly models the one real divergence in the current code (Area: slug `aor`, link word `area`) without inventing a naming convention that doesn't already exist. For the five types where slug and link word are the same string (Project/Life/Goal/Vision use the same word for both; Actions has no link word), callers simply pass the same string twice or omit the link word.
- **`link word` is optional (nil for Actions in this change).** When nil, the macro must skip generating the `org-link-set-parameters` call and the `*-insert-*-link` command entirely - it must not generate a link type with an empty/placeholder name. This keeps Actions' external surface identical to today (see Non-Goals) while still deduping its directory/list/ensure/find code through the same macro as everything else.
- **Default file content: a macro parameter accepting `nil`, a literal string, or a format-string applied to the entity name.** This covers all three existing cases (empty / static `"#+TODO: ...\n\n"` / `"#+TODO: ...\n\n* TODO %s\n"` with the name interpolated) without new abstraction.
- **New file `init-horizon-types.el` defines the macro; `init-projects.el` and `init-files.el` become call sites.** The macro must be defined (loaded) before any file that expands it. Rather than reordering `init-projects.el`/`init-files.el` relative to each other, add a new file loaded once, early, by both. `init.el` gains one new `(require 'init-horizon-types)` line, placed after `init-org` and before `init-files`/`init-projects` (both of which will now expand the macro at load time).
- **Keep the generated `find`/`ensure`/`follow`/`complete`/`insert-link` function bodies behaviorally identical to today's hand-written versions**, including the exact `completing-read` prompt strings (e.g. `"Project: "`, `"Area: "`) - these are currently type-specific strings, not derived from the slug/word (e.g. Area's directory slug is `aor` but its prompts read "Area: ", matching the link word not the slug). The macro takes the prompt strings as an explicit parameter rather than deriving them, to avoid silently changing user-visible prompt text during a refactor that promises zero behavior change.

## Risks / Trade-offs

- [First macro in a config that has used none so far; adds one more concept a future reader must understand] → Mitigation: keep the macro's body straightforward backquote/comma templating (no `cl-lib`, no recursive macro-generating-macros), and give it a thorough docstring/commentary block explaining the expansion, matching the file-header commentary convention already used throughout `lisp/*.el`.
- [Byte-compilation/load-order: if `init-horizon-types` isn't required before `init-projects`/`init-files` expand the macro, `require`/`load` will error or silently fall back to a stale/absent macro definition] → Mitigation: add the `require` immediately after `init-org` in `init.el` (task-level step), and manually verify a full `emacs --batch -l init.el` (or interactive restart) load succeeds with no byte-compiler "macro not known to be defined" warnings before considering the change done.
- [Subtle prompt-string or default-content divergence reintroduced during re-expression, e.g. accidentally deriving "Aor: " from the slug instead of keeping "Area: "] → Mitigation: tasks.md enumerates every one of the six types' exact current strings (prompts, default content, directory paths) to copy into the macro invocation, and a manual verification pass diffs `git diff` behavior-relevant strings against the pre-refactor file.
- [Actions staying without a link type (Non-Goal) means the follow-up archive change still has to add that link type before Actions can support "follow a link into an archived context file" the same way Project/Area/etc. do] → Accepted trade-off: flagged explicitly in Non-Goals and proposal.md as deferred to that change, not silently dropped.

## Migration Plan

Pure internal refactor within a single Emacs config repo, applied as a normal commit: no data migration, no `~/notes/**` content changes, no user action required. Rollback is a plain `git revert` of the commit(s), since no external state (files under `~/notes/`, `org-id-locations`, `org-roam.db`) is touched by this change - only Elisp source under `emacs/.config/emacs/lisp/`.
